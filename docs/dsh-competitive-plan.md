# DeepSeek Harness 対抗戦略・実行計画

> 状態: 計画（未着手） / 作成日: 2026-11-01 / 対象: Desktop 版 + Docker 版
> 関連: [`architecture.md`](architecture.md) / [`desktop/coding-agent-plan.md`](desktop/coding-agent-plan.md) / [`memory-roadmap.md`](memory-roadmap.md)
> 前提: 実装は実質 1〜2 名、期間は約 6 ヶ月（2026-11 〜 2027-04）。工数は人日。

---

## 0. 結論

1. **「何でもプラグイン」の土俵では戦わない。** DSH は Cordis を中心に据えた *開発者向けフレームワーク* であり、プラグインの数とエコシステムで正面から競うと負ける。
2. **MIX-agent は「ハーネスの運用層（control plane）」を取る。** 実行だけでなく、承認・監査・砂箱・常時稼働・記憶・マルチデバイスまでを一つの製品として提供する。
3. **DSH を敵ではなくバックエンドとして取り込む。** MCP / Skills / hooks / ACP を介して DSH・Claude Code・Codex を MIX から動かせるようにし、「安全に、手元で、ずっと動かす」で差別化する。

一言でいうと:

> **MIX-agent = 好きなハーネスを、自分の手元で安全に運用するためのワークスペース。**
> DSH は「ハーネスを組み立てる道具」。MIX は「組み上がったハーネスを、日常的に、安全に、止めずに使う場所」。

## 1. 前提: DSH は何に勝っていて、何を解いていないか

### 1.1 DSH の強み（2026-11 時点の公開情報）

| 領域 | 内容 | MIX への示唆 |
| :--- | :--- | :--- |
| アーキテクチャ | Cordis による「everything is a plugin」。モデルアダプタ、ツール、セッション、砂箱、ストレージ、エージェントループ、UI まで差し替え可能 | 真似しない。差し替え可能性は MIX の主戦場ではない |
| 実行プロファイル | `web` / `headless` / `sdk` / `sdk-minimal` / `acp` を同梱 | **headless / SDK / ACP の欠如は MIX の重大なギャップ** |
| セッション | 追記型イベントログ。resume / fork / search / replay / Trajectory view | 監査・デバッグの土台。MIX はイベントはあるが fork / replay が弱い |
| モード | Standard / PTC / Minimal / Creator。PTC は生成 SDK に対してコードを書かせ、`run_code` 経由でツールを呼ぶ | ツール呼び出しの「表現形式」は将来の差別化になり得る |
| 委譲 | `subagent-claude-code` / `subagent-codex` など、他ハーネスを子エージェントとして呼ぶ | **MIX も同じことを逆向きにやる（DSH を子にする）** |
| 互換 | Claude Code の `hooks.json` を読むブリッジ | hooks 互換は低コスト・高効果 |
| 経済性 | V4-Flash など極端に安いモデルと組み合わせ、agent を大量に走らせる前提 | コスト路由と予算管理で対抗。ローカルモデルは MIX の強み |
| コミュニティ | MIT、公開直後から巨大なスター数とプラグイン作者 | 数では追わない。ニッチと相互運用で取る |

### 1.2 DSH が解いていない（あるいは軽視している）運用課題

- **安定性**: developer preview を明言し、破壊的変更が続く。業務導入にはバージョン固定と検証が必須。
- **安全性**: 自ら「セキュリティ監査を受けていない」と明記。第三者が作ったプラグインは任意コード実行に等しい。
- **常時稼働**: ローカル開発者向けの色が強く、自宅鯖・NAS でのマルチユーザー運用、通知、定期実行、バックアップは利用者が組み立てる領域。
- **監査**: 「誰が、どのツールを、どの権限で、いつ実行したか」を組織として証明する仕組みは薄い。
- **ローカルモデル**: モデル非依存ではあるが、Ollama / LM Studio のライフサイクル管理、`num_ctx`、小型モデルの tool calling 安定化までは面倒を見ない。
- **日本語 / 国内運用**: ドキュメント・サポート・データ所在地の説明が日本語で揃っているわけではない。

これらはすべて、MIX-agent が既に部分的に持っている資産である。

### 1.3 戦わない領域（明示）

- Cordis 互換のインプロセス TS プラグインランタイム
- 任意コードを読み込むプラグインマーケットプレイス
- GitHub スター数・汎用フレームワークとしての知名度
- モデル学習・推論基盤
- 不特定多数向けのマルチテナント SaaS

## 2. 現状の資産とギャップ（v0.5.5）

### 2.1 既に持っている資産

| 資産 | 実装 | 競争上の意味 |
| :--- | :--- | :--- |
| 2 エディション | Desktop（Tauri/Rust）と Docker（FastAPI/React）。契約を parity 検査で同期 | 「手元」と「常時稼働」の両方を同一製品で提供できる |
| 承認と権限 | ツール単位の Allow / Ask / Deny、パス・コマンドのスコープ永続化 (`apps/desktop/tools/src/execute.rs`) | 自律性と安全のバランス。DSH の approval より運用向け |
| 砂箱・通信境界 | macOS `sandbox-exec`、Docker の非 root / read-only / egress-proxy | 「監査されていないハーネス」との明確な差 |
| エージェント品質 | 検証ループ、停滞検知、チェックポイント、steering、読み取り並列、coding eval (`apps/desktop/core/src/runs/`) | ベンチマークで語れる。DSH の Minimal 的な「素の実力」比較に耐える |
| 記憶 | embedding + 知識グラフ + ライフサイクル + recall bench（両版） | 長期運用の価値。プラグインではなく製品機能 |
| ローカル LLM | Ollama / LM Studio の検出・起動停止・モデル管理・`num_ctx` 制御 | DSH が持たない実用性。オフライン / 機密案件の入口 |
| ブラウザ | 実 Chromium の自動操作とライブ表示 | 調査・検証・RPA の導線 |
| 常時稼働 | スケジュール実行、webhook トリガ型、マルチユーザー、バックアップ | 自宅鯖・小規模チームの運用ニーズ |
| 相互運用の種 | MCP（stdio / HTTP）、`SKILL.md`、エージェントプロファイル (`tools/src/agent.rs`) | ここを拡張するのが最短の対抗策 |

### 2.2 ギャップ（優先順）

| # | ギャップ | 現状 | なぜ致命的か |
| :--- | :--- | :--- | :--- |
| G1 | **headless / CLI / SDK がない** | Tauri アプリのみ。`core` に bin は `retrieval-bench` だけ | 自動化・CI・他ツール連携の入口がなく、「ハーネス」を名乗れない。DSH の `headless` / `sdk` / `acp` に真っ向で負ける |
| G2 | **hooks がない** | なし | Claude Code / DSH 利用者の既存ワークフローを取り込めない。導入障壁が高い |
| G3 | **セッションの fork / replay / trajectory がない** | Run イベントはある (`packages/tool_contracts/run_events.json`)。UI は履歴再生中心 | 長期運用・監査・デバッグで DSH に劣る |
| G4 | **監査ログと組織ポリシーがない** | 承認履歴はあるが、改ざん防止・エクスポート・ポリシー配布がない | 「安全」を掲げるなら証明が必要。ここが最大の差別化候補 |
| G5 | **外部ハーネスの受け入れがない** | MCP のみ | DSH の「他ハーネスを子にする」に対し、MIX は自前エンジンだけ |
| G6 | **発見性・英語圏の情報が弱い** | README.en はあるが docs は日本語中心 | DSH の勢いに埋もれる |
| G7 | **公開ベンチマークがない** | `coding_eval` は内部 fixture のみ | 「DSH より良い」と言えない。再現可能な数値が必要 |

> G1〜G5 はすべて「プラグイン機能を増やす」よりも優先度が高い。プラグイン機構の拡張は MCP と hooks で代替できる。

## 3. ポジショニング

### 3.1 対象顧客（ICP）

1. **自分のマシン / 自宅鯖で、コードと認証情報を外に出さずにエージェントを常時動かしたい個人開発者**
2. **小規模チーム（2〜20 名）で、承認・監査・予算を効かせたいが、SaaS は避けたい**
3. **ローカル LLM を実用したいが、ツール呼び出しの不安定さで挫折した人**
4. **Claude Code / Codex / DSH を併用しており、散らばった実行を 1 か所で見たい人**

### 3.2 非対象

- とにかく安く大量に agent を回したいだけのユーザー（DSH + V4-Flash が最適）
- ハーネス自体を改造したい研究者（DSH が最適）
- 完全マネージドの SaaS を求める企業

### 3.3 提供価値の 3 層

```text
┌─────────────────────────────────────────────┐
│ Operate  常時稼働・記憶・スケジュール・通知 │  ← 自宅鯖 / NAS / チーム
├─────────────────────────────────────────────┤
│ Govern   承認・ポリシー・砂箱・監査・予算   │  ← 信頼の源泉
├─────────────────────────────────────────────┤
│ Run      自前エンジン + 外部ハーネス(DSH等) │  ← 実行の入口を広げる
└─────────────────────────────────────────────┘
```

DSH は主に「Run」の層を強くする。MIX は「Govern」と「Operate」で取り、Run は外部ハーネスも受け入れて広くする。

### 3.4 メッセージ案

- **「どのハーネスも、あなたの手元で。安全に、ずっと。」**
- "Bring your own harness. Keep your code, keys, and logs."
- 比較ページの軸: *プラグインの数* ではなく *承認の強さ / 監査 / 常時稼働 / ローカルモデル / データ所在地*。

## 4. 戦略の 4 本柱

### P1. 取り込む（Interop）

**狙い**: DSH / Claude Code / Codex の利用者を、MIX の UI・承認・記憶・スケジュールに迎え入れる。

- `mixd` CLI と headless モード（`mixd run`, `mixd serve`, `mixd acp`）
- Claude Code 互換 hooks（`PreToolUse` / `PostToolUse` / `SessionStart` / `Stop`）
- `SKILL.md` の探索パス拡張（`.mix/skills`, `.claude/skills`, `.dsh/skills`）
- 外部ハーネスアダプタ（DSH を子エージェントとして実行）
- ACP サーバ（Zed などのエディタから MIX を駆動）
- セッションの export / import（JSONL + Markdown）

**成功指標**: MIX の UI から DSH に 1 タスクを委譲でき、hooks で危険なコマンドを 1 つブロックできる。

### P2. 守る（Trust）

**狙い**: 「監査されていないハーネス」との差を、文書ではなく実装で示す。

- 両版共通のポリシー契約（`.mix/policy.toml`）
- 追記型・ハッシュチェーン付き監査ログ（ツール呼び出し、承認、拒否、設定変更）
- 砂箱の強化（Linux: bwrap / Landlock、Windows: Job Object / AppContainer、macOS: 既存 `sandbox-exec`）
- MCP サーバの許可リスト・バージョン固定・権限マニフェスト
- 秘密情報のマスク範囲をテストで固定（`tools/src/redact.rs`）
- 脅威モデルと `SECURITY.md` の更新、監査レポートの公開

**成功指標**: ある Run の「誰が・何を・どの権限で」を監査ログだけで再構成できる。砂箱テストが CI で回る。

### P3. 常時稼働（Operate）

**狙い**: DSH が苦手な「止めない運用」を製品にする。

- `mixd serve`（headless）+ 既存 Web UI の接続
- Desktop 版にもスケジュール / webhook / 通知を展開
- マルチユーザーのロールとユーザー別予算（Docker 版）
- PWA / モバイル承認
- 定番テンプレート（日次ダイジェスト、Issue トリアージ、バックアップ確認）

**成功指標**: NAS 上で定期実行が回り、スマホから承認できる。

### P4. 品質とコスト（Quality）

**狙い**: 「安いモデルでも、ローカルでも、最後まで終わる」ことを数値で示す。

- コスト認識ルーティング（読取は安いモデル、編集は強いモデル、失敗時はエスカレーション）
- モデルプロファイル（local / cheap / strong）と予算の連動
- `repo_map` と LSP 相当の diagnostics（`coding-agent-plan.md` 10.5 の残り）
- 公開ベンチマーク（fixture repo + 再現手順 + DSH 比較）
- Memory の共有パック化（プロジェクトをまたぐ recall）

**成功指標**: 公開ベンチで「検証まで完了したタスク単価」を DSH 比で 30〜40% 下げる。

## 6. 判断ゲート（やめる勇気）

| 時点 | 判断 | 条件 | 選ぶ道 |
| :--- | :--- | :--- | :--- |
| Phase 1 終了 | 外部ハーネス連携を続けるか | DSH アダプタの利用が 4 週間で全 Run の 5% 未満 | アダプタを実験扱いに下げ、ACP と hooks に集中 |
| Phase 2 終了 | 監査・ポリシーに投資を続けるか | 設計パートナー（社内利用含む）が 1 件も得られない | 実装は維持し、エンタープライズ向け追加開発は停止 |
| Phase 3 終了 | エンジンを統合するか | 統合コストが 6 週間超、または parity テストの維持が月 3 日超 | **A: 二重エンジン維持**（契約検査を強化） |
| Phase 3 終了 | 統合する場合の方式 | 統合コストが 6 週間以内 | **B: Rust コアを sidecar 化**し、Python は API / UI / 認証に専念（C: 全面書き換えは選ばない） |
| 随時 | プラグイン機構を作るか | MCP + hooks で 90% の要望が満たせない | 満たせない場合のみ、プロセス分離の拡張機構を検討 |

**エンジン統合の補足**: 現状の二重実装は最大の技術的負債。ただし「契約を揃える」だけでも運用は成立している。統合は *headless が主要導線になった場合* にだけ投資する。DSH が 1 ランタイムで戦っている以上、ここを放置すると中長期で速度差が出る。

## 7. KPI

| 指標 | 定義 | 基準（Phase 0） | v1.0 目標 |
| :--- | :--- | :--- | :--- |

## 8. やらないこと

- **Cordis の再実装**。インプロセスで任意の TS プラグインを動かす設計は、安全性と保守性の両面で割に合わない。
- **プラグインマーケットプレイスの運営**。審査・署名・責任のコストが高く、1〜2 名では持続しない。MCP サーバのキュレーションで代替する。
- **DSH の機能追跡**。四半期ごとに「向こうが足した機能」を追うとロードマップが崩れる。追うのは *運用課題* だけ。
- **Windows 砂箱の完璧さ**。需要を確認するまで best-effort + コンテナ推奨に留める。
- **マルチテナント SaaS / 課金基盤**。セルフホストに集中する。
- **独自モデル / 推論基盤**。

## 9. リスクと対策

| リスク | 影響 | 対策 |
| :--- | :--- | :--- |
| DSH が高速に進化し、運用機能も取り込む | 差別化が消える | 追わない。MIX は「DSH を動かす場所」として相互運用を深める。最悪、DSH のディストリビューションになる選択肢を残す |
| 外部ハーネスの実行がセキュリティ責任を増やす | 信頼喪失 | プロセス分離・砂箱・明示的な同意・「非保証範囲」の文書化。既定では無効 |
| 二重エンジンの保守で速度が落ちる | リリース遅延 | parity 検査を CI に固定。Phase 3 で統合判断。新機能は `mixd` 側を先行し、server は契約アダプタで追従 |
| 1〜2 名の帯域不足 | 中途半端 | Phase ごとのゲートと撤退条件。四半期で 1 テーマに絞る |
| 「安全」を掲げて脆弱性が出る | 信用の致命的損失 | 監査・砂箱・redaction のテストを先に。保証ではなく「境界と限界の明示」に徹する |
| ローカルモデルの品質が目標に届かない | 差別化の崩壊 | 早めにベンチ。届かない場合は「クラウドモデル + プライバシー」に訴求を寄せる |
| DSH の破壊的変更でアダプタが壊れる | 互換性の信頼低下 | バージョン固定・起動時検査・互換表・CI の nighty 検証。壊れたら明示的に落とす |

## 付録 A. DSH 比較の実測方法（再現可能にする）

1. **固定するもの**: モデル（例: 同一の DeepSeek V4 Flash / Pro、同一のローカルモデル）、温度、最大ステップ、fixture repo の commit。
2. **タスク**: 修正、リファクタ、テスト修復、探索のみ、拒否すべき危険操作の 5 種 × 2 難度。
3. **測るもの**: 成功率（独立した検証コマンドで採点）、所要時間、入力/出力トークン、コスト、ツール呼び出し数、承認回数、人手介入回数。
4. **記録**: `docs/benchmarks/<date>-<harness>.json` に生データ、Markdown に要約。実行スクリプトを `scripts/bench/` に置く。
5. **注意**: DSH は developer preview で挙動が変わる。バージョンと commit を必ず併記する。MIX 側も同一条件で走らせる。

## 付録 B. 用語

| 用語 | 意味 |
| :--- | :--- |
| ハーネス | モデルにツール・セッション・砂箱・ループを与えるランタイム |
| control plane | 実行そのものではなく、実行の統制・監視・運用を担う層 |
| ACP | Agent Client Protocol。エディタなどがエージェントを駆動するためのプロトコル |
| hooks | ツール実行前後やセッション開始時に外部コマンドを挟む仕組み |
| parity | Desktop 版と Docker 版で契約・挙動を一致させること |
