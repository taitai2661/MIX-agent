> 状態: 実装中（Phase 0〜1。詳細は「0.1 実装状況」）
> 対象: `apps/desktop/ui` / `apps/desktop/app`（Tauri シェル）
> 最終更新: 2026-11-06
> 関連: [`ui-conventions.md`](ui-conventions.md) / [`performance-plan.md`](performance-plan.md) / [`architecture.md`](architecture.md)
>
> **方針決定（2026-11-06）**: チャット / コーディングの2面は**残す**。
> 統合せず、切り替え・履歴・プロジェクトの関係を明示して「消えた」と
> 感じさせないことを優先する。

## 0. 結論

個々の画面は作り込まれ、性能対策も入っている。しかしプロダクト全体としては
**「機能の一覧」がUIになっており、ユーザーの目的（質問する / 作業を任せる /
結果を確認する）に沿った一つの流れになっていない**。これが「とにかくUXが悪い」
という印象の主因だと考える。

特に効いているのは次の5つ。

1. **ワークスペースが2つに分裂している**（チャット / コーディング）。
   履歴・新規作成・モード・プロジェクトの扱いが別世界で、切り替えると
   「さっきまで見ていたものが消えた」ように感じる。
2. **同じ操作が複数箇所にある**（承認、検索、新規作成、設定）。
   どこを押せばよいか予測できず、承認に至ってはチャットから設定画面へ
   飛ばされる。
3. **設定が17タブあり、保存方式も混在している**。
   「どこで変えるのか」「保存したのか」が分からない。
4. **タイトルバーにアイコンが密集している**。
   ファイルツリー / 変更 / ブラウザ / 使用量 / アクティビティがラベルのない
   アイコンで、初見では意味が推測できない。
5. **本文が 13px、補助が 12/11px 中心の高密度タイポグラフィ**。
   日本語では小さく、疲れる。高機能さより「窮屈さ」が先に伝わる。

進め方は **「測る → 小さく直す → 情報設計を統合する → 中核ループを磨く」**。
最初の2週間は IA を壊さずに効く直近の改善（承認・検索・文字・現在地）を行い、
その結果を見てからワークスペース統合に踏み込む。各 Phase は独立して
リリース可能とし、既存の性能計画を退行させない。

## 1. 前提

- これは**機能追加ではなくUX改善**の計画。新しい能力を増やすより、
  すでにある能力に到達できるようにする。
- 「UXが悪い」を主観のまま実装しない。Phase 0 で代表ジャーニーを計測し、
  改善前後の比較基準を持つ。
- 計測は**ローカル完結**を基本にする（外部テレメトリは送らない）。
  既存の `performance.mark` と Diagnostics の仕組みを拡張する。
- 既存の [`performance-plan.md`](performance-plan.md) で実装済みの
  仮想スクロール、イベントバッチ、コード分割、ペイロード削減は**触らない**。
- 深いリンク（Spotlight / ネイティブメニュー / ⌘K）とキーボード操作を
  壊さない。IA を変えるときは旧導線を1リリース残す。

## 3. 目標とする体験

### 3.1 原則

1. **2つの面を、1つのナビゲーションで説明する**
   チャットとコーディングは残す。ただし切り替えは常に見え、
   「履歴は消えていない」「今どちらの面にいるか」が分かるようにする。
   プロジェクトはコーディング面の文脈として明示する。
2. **現在地が常に分かる**
   選択中のスレッド、プロジェクト、実行状態、承認待ちを一箇所に集約する。
3. **一つの操作は一つの場所**
   承認、検索、新規作成、設定の入口を統一する。同じ目的のボタンを
   2箇所以上に置かない。
4. **段階的開示**
   最初に見せるのは3つまで。詳細（Base URL、MCP、診断、バックアップ）は
   「詳細設定」に畳む。
5. **失敗から戻れる**
   すべての失敗に、理由・再試行・取り消し・代替手段のいずれかを用意する。

### 3.2 目指す最初の体験

1. 起動 → **ゴール選択**（「質問したい」 / 「フォルダで作業したい」）
2. モデル: ローカル検出、またはプリセット選択。
   Base URL などは「詳細」に隠す。
3. フォルダ: 選択（任意）。選ばなくてもチャットは始められる。
4. 例文を1クリック → 最初の応答。

目標: **インストールから最初の応答まで3分以内**（ローカルモデル検出時）。
API キー入力はクラウドを選んだ場合だけ。

### 3.3 目指す日常の体験

- サイドバーには**現在の面の履歴**が並び、上部に「チャット / コーディング」
  の切り替えと、反対側の履歴への導線が常に見える。切り替えても
  「履歴が消えた」と誤解させない。
- 何かを始めるときは、その面の「新規」ボタン1つ。現在のプロジェクト・
  モデルを引き継ぎ、必要なら開始シートで変更する。
- 実行中はコンポーザー上に**1本のステータスバー**（状態 / ツール / 経過 /
  停止 / 介入）。右パネルを開かなくても分かる。
- 承認は**その場で**解決できる。承認一覧はグローバルな受信箱として
  いつでも開けるが、会話から離れない。
- 設定は6カテゴリ。変更は即時保存＋「元に戻す」、または明示保存の
  どちらかに統一する。

## 4. ロードマップ

### Phase 0 — ベースライン計測（2〜3日）

**最初にやる。** これがないと、後の変更が「好み」になる。

- 代表ジャーニーを5つ決め、現状の所要時間・クリック数・離脱点を記録する。
  1. 初回起動 → 最初の応答
  2. 新規スレッドを開始 → 送信
  3. 承認待ちを解決
  4. 設定を変更して保存
  5. 過去のスレッドを検索して開く
- ローカル計測を追加する（外部送信なし）。
  - `first_message_sent` / `first_token` / `run_completed`
  - `approval_shown` / `approval_decided`（場所・所要時間）
  - `settings_opened` / `settings_saved` / `settings_save_failed`
  - `surface_switched` / `panel_opened` / `search_used` / `error_shown`
- 既存の `performance.mark("shell-ready")` / `transcript-ready` と
  Diagnostics を拡張し、`docs/desktop/ux-baseline.md` に記録する。
- 5名程度のモデレートテスト（社内ドッグフーディング可）。
  観察項目: 「今どこにいるか」「次に何を押すか」「なぜ失敗したか」。

**完了条件**: 改善前の数値と、上位10個の摩擦ポイントが文書化されている。
**この Phase ではUIを変えない。**

### Phase 1 — 直近の改善（1週間 / P0）

IA を壊さず、体感を大きく変える。

1. **承認を会話から離さない**
   - ヘッダーの承認インジケーターを、設定への遷移ではなく
     **承認ドロワー**（その場で承認 / 拒否 / 常に許可）に変える。
   - チャット内のバナーとカードは残すが、判断は1つのコンポーネントに集約。
   - 対象 Run / ツール / 差分 / 期限が同じ画面で分かる。
2. **検索の入口を常設**
   - 広い画面は検索フィールド、狭い画面はアイコン。⌘K は維持。
   - サイドバーのローカル絞り込みとコマンドパレットの違いをラベルで説明。
   - スレッド・メッセージ・プロジェクト・設定を横断。
3. **タイトルバーを減らす**
   - 直接操作は「ファイルツリー」「ブラウザ」まで。
   - 「変更」「使用量」「アクティビティ」は1つの「表示」メニューへ。
   - 直接操作にはツールチップと `aria-label` を付け、メニュー側で
     ラベル付きの一覧を見せる。
4. **文字と行間**
   - 本文 14px、補助 12px、メタ 12px を下限にする（11pxは原則廃止）。
   - 日本語の行間を 1.6〜1.7 に上げる。
   - コントラストを AA で再確認。
5. **ワークスペース切り替えの意味を明示**
   - ドロップダウンではなく、**セグメント（チャット / コーディング）** にする。
   - 切り替え時に「履歴は消えていない。フィルタが変わるだけ」と分かる
     空状態・フィルタチップを出す。
   - プロジェクト未選択時の導線を1つに。
6. **失敗からの回復**
   - 主要なエラーに「再試行」「取り消し」「設定を開く」のいずれかを付ける。
   - 失敗した操作の入力を失わない。

**完了条件**: 5ジャーニーで「どこを押すか分からない」が0。
承認が会話から2クリック以内。800px幅で検索に到達できる。

### Phase 2 — 2面の関係を明確にする（2週間 / P1）

**統合はしない。** 2つの面を残したまま、履歴とプロジェクトの関係を
ユーザーが説明できる状態にする。

- **サイドバー上部に面の切り替えを固定**。現在の面の履歴であることを
  見出しで示し、反対側の面の件数と「◯件の履歴」を併記する。
- **切り替え時の文脈保持**。スクロール位置・選択スレッド・下書きは
  面ごとに保持し、戻ったときに復元する。
- **プロジェクトの扱いを明示**。コーディング面ではプロジェクトが
  必須であることを、未選択時の空状態とコンポーザーで説明する。
  チャット面からプロジェクトを選んだ場合は「コーディング面で使う」
  ことを予告して切り替える。
- **ナビゲーションを整理**:
  「スレッド」「プロジェクト」「自動化」「設定」＋現在の面。
  エージェントプロファイル・スケジュール・ナレッジは適切な親の下へ。
- **新規作成の語彙を統一**。`新規チャット` / `新規タスク` は残してよいが、
  どちらの面の操作かがボタンと空状態から分かるようにする。
- **モードはコンポーザーに集約**（チャット / 思考 / エージェント / 計画）。
  「どの面にいるか」ではなく「今回何をさせるか」として選ぶ。
- **旧導線のリダイレクト**。Spotlight / メニュー / ⌘K から反対の面の
  スレッドを開くときは、面を切り替えてから開く（現在も一部実装済み）。

**完了条件**: ユーザーが「今どちらの面か」「履歴はどこにあるか」を
説明できる。面を切り替えても下書き・スクロール・選択が失われない。
主要タスクの80%が2クリック以内に開始できる。

### Phase 3 — 中核ループを磨く（2週間 / P1）

- **Run ステータスバー**（コンポーザー上）:
  状態 / 実行中のツール / 経過時間 / 停止 / 介入 / 承認待ち。
- **ツールコールのインライン表示**:
  「何を / どこに / 結果どうなったか」を折りたたみで。詳細は右パネルへ。
- **承認受信箱**:
  全 Run の承認待ちを一覧。差分・引数・期限・Run へのリンク。
  承認 / 拒否 / 常に許可 / このセッションで許可を同じ語彙で。
- **失敗の回復**:
  再試行 / 再生成 / 編集して再実行 / 停止 / 取り消し。
  エラー文は「原因 + 次の一手」の2文にする。
- **ストリーミングの状態**:
  「考え中」「ツール実行中」「応答中」「承認待ち」を区別する。

**完了条件**: 右パネルを開かなくても実行状態が分かる。
承認の平均解決時間が Phase 0 比で半減。

### Phase 4 — 設定とパネル（2週間 / P2）

- **設定を6カテゴリに再編**:
  一般 / モデルと接続 / エージェント / データと検索 / 外観 / 詳細・診断。
  低頻度（バックアップ、診断、Spotlight、MCP の詳細）は「詳細」へ。
- **保存方式を統一**:
  即時保存＋「元に戻す」トースト、または明示保存のどちらか。
  「保存」ボタンと即時保存を同じ画面に混在させない。
- **設定検索を強化**: ラベルだけでなく説明・値を検索。
- **右パネルを整理**: 3モード（アクティビティ / 変更 / ブラウザ）に絞り、
  ファイルプレビューは変更パネル内へ。幅・dock 状態を記憶し、
  狭い画面ではオーバーレイに固定。
- **狭いウィンドウ**: 設定レールをアイコン＋ツールチップで残す。
  検索は常設アイコン。

**完了条件**: 設定タスクの成功率90%以上。保存の取り違え0。
右パネルの開閉で中央カラムが予期せず縮まない。

### Phase 5 — 仕上げと退行防止（1週間 / P2）

- キーボードのみで5ジャーニーを通す。フォーカス順・復帰・Esc を確認。
- スクリーンリーダー（VoiceOver）で主要画面を確認。
- 200% ズーム、IME（日本語入力）、reduced motion、高コントラスト。
- バンドル / 起動時間の budget を維持（既存CI）。
- 文言の棚卸し: 実装用語をユーザー語に置換（Run → 実行、など）。
- 新規フローの UI テストを追加（Vitest / Testing Library）。

## 8. 非目標 / リスク

### 非目標

- ビジュアルデザインの全面刷新（トークンと原則は維持する）。
- 機能の追加（新しいツール、新しいプロバイダー）。
- 外部テレメトリの導入。
- パワーユーザー向け機能の削除。詳細設定へ移すだけ。

### リスクと対策

| リスク | 対策 |
| :--- | :--- |
| IA 統合で既存の深いリンクが壊れる | 旧 `surface` / `view` を1リリース残し、リダイレクトする |
| 履歴統合で「前の作業」が見つからなくなる | プロジェクト / モードのフィルタと検索を同時に出す |
| 承認ドロワーがフォーカスを奪う | 非モーダル。開いてもコンポーザーの入力を維持 |
| 文字を大きくして一画面の情報量が減る | 密度設定（コンパクト / 標準）を用意する |
| 設定再編で迷う | 旧タブ名からの検索ヒットと「移転しました」表示 |
| 性能退行 | 既存の bundle / startup ゲートを維持 |

## 9. 最初の2週間（具体タスク）

1. **Day 1–2**: 5ジャーニーの現状計測。`docs/desktop/ux-baseline.md` 作成。
   ローカルイベントの最小実装。

6. **Day 10**: サーフェス切り替えのセグメント化と説明文。

   Phase 1 の検証。改善点を修正。

## 10. 決定事項と残りの確認

### 決定済み（2026-11-06）

1. **2面は残す。** チャット / コーディングを統合せず、切り替えと履歴の
   関係を明示する。Phase 2 は「統合」ではなく「明確化」として進める。
2. **実装は Phase 0 から順番に進める。**

### 残りの確認

1. **主対象ユーザーは開発者か。**
   開発者中心なら密度は許容し、用語と導線を優先する。
   非開発者も含むなら、初回体験と設定の簡略化を優先する。
2. **13px は意図したブランドか、単なる密度調整か。**
   意図でなければ Phase 1 で 14px に上げる。
3. **ローカル計測の保存期間と見せ方。**
   Diagnostics に出すだけか、設定で OFF にできるようにするか。
